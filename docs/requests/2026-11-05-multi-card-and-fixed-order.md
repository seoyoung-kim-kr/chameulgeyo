## 1. 카드 종류별로 관리

### 요청 원문

> 카드 종류별로 할 수 있도록 (나는 카드가 한 개인데 이 사람은 여러 개래)

### 지금 구조 (카드 한 장 전제)

카드 한 장 전제가 여러 곳에 박혀 있다. 화면만 고쳐서는 안 되고 데이터 모델부터 바뀌는 일이다.

| 위치 | 한 장 전제 |
|---|---|
| `settings.card_cutoff_day`, `settings.card_pay_day` | 사용자당 확정일·출금일이 하나뿐 |
| `card_bills` unique(`user_id`, `due_date`) | 카드 구분 없음. 출금일이 같은 두 카드는 한 행으로 합쳐짐 |
| `lib/bills.ts` `upsertCycleBill` | 주기당 대금을 한 건으로 맞추고, 나머지는 **지운다** |
| `app/(app)/card/` | 이번 주기·다음 주기 대금을 각 1건만 입력 |
| `fixed_expenses.payment_method` | `'card'`만 있고 어느 카드인지 없음 |
| `card_bills.includes_card_fixed` | 카드 고정지출 **전체**를 한 대금에 더함 |
| `lib/decisions.ts` `addToBill` / 환불 | "산다" 금액을 단일 확정일·출금일로 계산한 대금에 더하고 뺌 |

반면 `lib/cashflow.ts`의 `summarizeBills`는 이미 주기 안의 대금 여러 건을 합산한다. 계산 쪽은 여러 건을 받아들일 수 있고, 막는 건 쓰기 경로(`upsertCycleBill`)와 입력 UI다.

### 먼저 확인할 것 (요청자에게)

현금 흐름은 **급여 주기 단위**로 센다. 카드가 몇 장이든 출금일이 전부 같은 주기 안에 떨어지면, 지금도 카드 앱 숫자를 합쳐서 한 번에 넣으면 계산 결과는 같다. 그래서 "여러 장"이 실제로 무엇이 불편한지부터 확인해야 범위가 정해진다.

1. 카드가 몇 장이고, 각 카드의 **결제일(출금일)·확정일**이 언제인가?
   - 출금일이 서로 다른 급여 주기에 걸치는가? (예: 월급일 25일인데 A카드 1일, B카드 26일 출금)
2. 불편한 지점이 어디인가?
   - (a) 카드 앱 숫자를 직접 더해서 넣는 게 귀찮다 → 입력만 카드별로 나누면 됨
   - (b) 출금일이 달라서 어느 주기에서 빠지는지 틀린다 → 대금·출금일을 카드별로 가져야 함
   - (c) "산다"로 산 물건이 어느 카드 대금에 들어갈지 맞아야 한다 → 구매 흐름에 카드 선택 필요
   - (d) 고정지출이 어느 카드로 나가는지 구분하고 싶다
3. 체크카드도 "카드"로 넣으려는가? (지금 앱은 체크카드·계좌 지출을 생활비로 본다)

### 범위 안 (선택지)

**A. 최소안 — 카드 엔티티 없이 대금만 여러 건**
- 주기당 대금 여러 건 허용 (`upsertCycleBill`의 "나머지 삭제" 제거, 입력 UI에 행 추가)
- 각 행에 이름(메모)·금액·출금일
- "산다"는 여전히 기본 확정일·출금일 하나로 계산 → (c)는 해결 안 됨
- 해결: (a), (b) 일부. 마이그레이션 작음

**B. 정식안 — `cards` 테이블 도입**
- `cards`: id, user_id, name, cutoff_day, pay_day, sort, archived_at
- `card_bills.card_id` 추가, unique를 (`card_id`, `due_date`)로
- `fixed_expenses.card_id` (payment_method = card일 때)
- `includes_card_fixed`는 그 카드의 고정지출만 더하도록
- `decisions.card_id` → "산다" 시 카드 선택, 대금 가산·환불도 그 카드 기준
- 기존 데이터: 사용자마다 "카드 1"을 만들고 `settings`의 확정일·출금일과 기존 대금·고정지출을 연결
- 해결: (a)~(d) 전부. 대신 변경 범위가 큼 (스키마·마이그레이션·설정 마법사·카드값 화면·구매 판정 흐름·환불·테스트)

### 우려

- **핵심 흐름이 무거워진다.** 앱의 중심은 "살까? → 판정 → 산다/안 산다"인데, B안은 여기에 카드 선택이 끼어든다. 카드 한 장 쓰는 사용자(현재 주 사용자)에게는 순수한 손해다. 카드가 1장이면 선택 단계를 숨기는 처리가 필수.
- **입력 부담이 카드 수만큼 늘어난다.** 이 앱은 카드사 앱 숫자를 손으로 옮겨 적는 구조라 카드 3장이면 매 주기 6칸(이번·다음 × 3)을 채워야 한다. 요청자가 실제로 그걸 할지 의문이다.
- 요청자가 한 명이다. 현재 주 사용자는 필요 없는 기능이므로, (b)·(c)가 실제 문제로 확인되기 전에는 A안 또는 "합산 입력 안내"로 충분할 수 있다.

### 범위 밖

- 카드사 연동·자동 조회
- 카드별 한도·실적 관리

## 2. 고정지출 순서 변경

### 요청 원문

> 고정지출 순서 변경 기능

### 지금 구조

- `fixed_expenses.sort` 컬럼이 이미 있다. 저장할 때 배열 순서대로 0, 1, 2… 를 넣고 (`app/(app)/setup/actions.ts`), 읽을 때 `sort` 오름차순 (`lib/ledger.ts`).
- 다음 주기 설정은 직전 주기 고정지출을 그 순서대로 기본값으로 가져온다 (`SetupLoader.tsx`).
- 새 항목은 항상 맨 아래에 추가되고, 옮길 방법이 없다.

→ **DB·서버 변경 없이 설정 마법사 2단계 UI만 고치면 된다.** 배열 순서만 바꾸면 기존 저장 로직이 그대로 `sort`에 반영한다.

### 방식

| 방식 | 장점 | 단점 |
|---|---|---|
| 위/아래 버튼 | 라이브러리 불필요, 접근성 좋음, 모바일 스크롤과 안 부딪힘 | 멀리 옮기려면 여러 번 눌러야 함 (최대 30개) |
| 드래그 핸들 | 직관적 | 라이브러리 추가(예: dnd-kit), 모바일에서 스크롤·키패드와 터치 충돌 조심 |

권장: 위/아래 버튼부터. 항목 수가 보통 한 자릿수라 충분하고, 불편하다는 말이 나오면 드래그로 바꾼다.

### 확인할 것

- 고정지출 **목록이 개별로 보이는 곳은 지금 설정 마법사뿐**이다. 홈·지난 주기 화면은 계좌/카드 합계만 보여준다. 요청자가 순서를 바꾸고 싶은 이유가 "입력 화면 정리"인지, "어딘가에 목록으로 보고 싶다"인지 확인 필요. 후자라면 이 요청은 순서 변경이 아니라 "고정지출 목록 보기" 요청이다.

### 범위 밖

- 이름·금액·결제수단 기준 자동 정렬 (요청 없음)

## 3. 구매할 때 결제수단(카드/계좌) 선택

### 출처

1번 요청을 검토하다 나온 것 (2026-11-06, 내부). 카드 여러 장과 무관하게 **지금 카드 한 장 사용자에게도 해당**한다.

### 지금 동작

"산다"를 고르면 결제수단을 묻지 않고 **무조건 신용카드로 산 것**으로 처리한다.

- `lib/decisions.ts` `addToBill`: 구매 금액을 확정일·출금일로 계산한 카드 대금에 더한다
- `lib/ledger.ts` `readReserves`: "산다" 구매 전부를 카드 결제 준비금으로 본다. 그 대금이 출금되는 주기 현금에서 그만큼 덜 뺀다
- 환불(`refundPlan`)도 카드 확정 전/후 기준으로만 계산한다

### 계좌·체크카드로 샀을 때 틀어지는 점

1. 산 직후: 카드 대금이 구매액만큼 부풀어 보인다. 준비금도 같은 금액이라 현금 계산은 상쇄돼 맞는다.
2. 나중에 카드 앱 숫자로 대금을 덮어쓰면: 대금에서는 그 구매가 빠지는데, 준비금은 계속 남는다. 준비금이 **다른 실제 카드 사용분을 상쇄**해서 그 주기 현금이 구매액만큼 **많게** 계산된다. 돈은 이미 계좌에서 나갔으므로 예산이 실제보다 여유 있어 보이는 쪽으로 틀린다 (위험한 방향).
3. 환불: 계좌 결제는 바로 돌아오는데, 카드 대금 차감으로 처리된다.

이건 기능 요청이라기보다 **현재 계산의 결함**에 가깝다. 이 앱으로 산 물건을 계좌·체크카드로 결제한 적이 있다면 지금도 영향이 있다.

### 바꿀 것

- `decisions.payment_method` 추가 (`'card' | 'account'`, 기존 행 null = 카드로 본다 → 지금 계산 유지)
- "산다" 흐름에 결제수단 선택 추가
  - 마찰을 줄이려면 마지막 선택을 기본값으로 둔다. 매번 묻는 대신 "카드로 기록 · 바꾸기" 정도로.
- `addToBill`, `readReserves`: `card`인 구매만 대상
- `account` 구매: 쇼핑 예산에서 바로 빠지는 것으로 끝 (대금·준비금 없음)
- 환불: `account`면 확정일 계산 없이 바로 예산 복구 (`refund_before_billing = true`와 같은 처리)

### 1번(카드 여러 장)과의 관계

같은 선택 칸이다. 1번 B안으로 가면 이 선택지가 "계좌 / 카드 A / 카드 B …"로 늘어날 뿐이다. 그래서 **3번을 먼저 하고, 1번은 그 선택지를 확장하는 식**으로 순서를 잡는 게 맞다. 3번만 먼저 해도 1번 B안의 `decisions.card_id` 부분 설계가 반쯤 끝난다.
