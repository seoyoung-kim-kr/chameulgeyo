## 1. 지금 계산식

예시 설정으로 설명한다: 월급일 5일, 카드 확정일 24일, 카드 출금일 5일.
이번 주기 = 11/5 ~ 12/4, 다음 주기 = 12/5 ~ 1/4.

```
이번 주기 현금  cash     = 월급 − 계좌 고정지출(미분류 포함) − 이번 주기 출금 카드값 중 월급에서 내는 부분
                월급에서 내는 부분 fromCash = max(카드값 − 준비금, 0)
                (카드값에 카드 고정지출이 아직 없으면(includesCardFixed=false) 카드 고정지출을 더한 뒤 계산)

쇼핑 예산      shoppingRaw = cash − 생활비 목표 − 비상금 − 이번 주기에 "산다"로 기록한 금액 합
               shopping    = max(shoppingRaw, 0)
생활비(현재)   livingNow   = 생활비 목표 + min(shoppingRaw, 0)      ← 쇼핑 예산이 마이너스면 그만큼 생활비가 준다
                                                                     비상금은 건드리지 않는다

판정           price ≤ shopping → 초록
               price >  shopping → 빨강, 넘은 금액 = price − shopping, 산 뒤 생활비 = livingNow − 넘은 금액

다음 주기 예상 현금 nextCash = 월급 − 계좌 고정지출 − 다음 주기 출금 카드값 중 월급에서 내는 부분
               (다음 달 월급·고정지출은 이번 달과 같다고 본다)
```

**준비금(reserve)**: 앱에서 "산다"로 산 카드 구매. 이번 주기 쇼핑 예산에서 이미 뺐으므로, 그 구매가 들어간 카드값이 출금되는 주기에서는 그 금액만큼 월급에서 덜 뺀다. 구매일 → 출금일은 `statementDueDate`(확정일·출금일)로 계산한다.

한 줄 요약: **지금은 카드로 사도 현금으로 산 것과 똑같이 계산한다.** 이번 달 쇼핑 예산에서 바로 빠지고, 그 돈은 카드값용으로 묶인다. 다음 달 현금은 줄지 않는다.

파일: `lib/cashflow.ts`(현금), `lib/budget.ts`(예산·판정), `lib/ledger.ts`(DB → 계산), `lib/decisions.ts`(산다/환불), `lib/cycle.ts`(날짜).

## 3. 발견한 구멍

### H1. 생활비 마이너스가 다음 달로 넘어가지 않는다 (정책 + 계산)
- 생활비가 0 밑으로 내려가면 실제로는 비상금이나 계좌 잔고가 깎이는데, 다음 주기는 깨끗하게 시작한다. 돈이 사라진다.
- 생기는 경로: (a) 빨강 구매, (b) 카드값을 뒤늦게 올려 적어 현금이 줄어듦, (c) 재설정으로 월급·고정지출을 바꿈.
- 대응: (a)는 아래 4절 흐름에서 막는다. (b)(c)는 남는다. 홈에서 "생활비가 X원 모자라요. 비상금에서 나가요" 정도로 **보여주기만** 해도 숨기는 것보다 낫다. 자동 이월은 복잡도 대비 이득이 적다 → 보류.

### H2. 결제수단 없음 (요청 문서 3번, 계산 결함)
- 계좌로 산 걸 카드로 처리 → 카드값 덮어쓰기 뒤 현금 과대 계산. 위험한 방향.

### H3. 주기 설정 저장이 카드 고정지출 포함 여부를 잘못 물려받는다 (코드 버그)
- `addToBill`이 만든 카드값 행은 `includesCardFixed=false`다 (앱에서 산 금액만 있으므로 맞음).
- 다음 주기 설정 마법사에서 그 행이 "이번 카드값"이 된다. 사용자는 카드 앱의 실제 청구액(고정지출 포함)을 적는다.
- 그런데 `saveMonth`는 `upsertCycleBill(…, { amount })`만 넘기고, `upsertCycleBill`은 `includesCardFixed`를 기존 값(false)으로 유지한다 (`lib/bills.ts`).
- 결과: 카드 고정지출이 **한 번 더 빠진다**. 마법사 미리보기는 `includesCardFixed: true`로 계산하므로 미리보기와 저장 결과가 다르다.
- 재현: 11월에 앱에서 카드로 한 건 산다 → 12/5 설정 마법사에서 카드값 입력 → 홈의 "이번 월급에서 낼 돈"이 카드 고정지출만큼 크다.
- 피하는 경로: 설정 전에 카드값 화면에서 저장하면 거기선 명시적으로 true를 넘긴다.
- 수정: `saveMonth`에서 `includesCardFixed: true`를 명시. 한 줄.

### H4. 출금 후 환불인데 환불이 들어갈 카드값 행이 없으면 환불이 사라진다
- `cancelInternal`: 환불 대상 주기에 카드값 행이 없으면 아무것도 안 한다 (주석에 "대금은 건드리지 않는다").
- 출금 후 환불의 대상은 "오늘 기준 다음 청구"라 아직 행이 없을 수 있다 (예: 확정일 뒤에 환불하면 다다음 주기).
- 결과: 환불금이 앱 어디에도 반영되지 않는다. 보수적 방향이지만 돈이 사라진다.
- 수정: 행이 없으면 음수 대신 `0`으로 만들고 "환불 예정 X원"을 따로 기록하거나, 그 주기에 행을 만들어 두고 카드 앱 숫자로 덮어쓸 때 안내. 또는 `card_bills.amount`가 음수를 허용하지 않으므로 별도 컬럼 `refund_pending` 필요. 빈도는 낮다 → 우선순위 낮음.

### H5. 카드값 옮겨 적는 타이밍
- 카드로 산 직후 카드사 앱에 아직 안 올라온 상태에서 다음 카드값을 옮겨 적으면, 카드값에는 그 구매가 없는데 준비금은 있다 → 다음 달 현금 과대 (일시적, 다시 적으면 풀림).
- 수정 아님, 안내 문제. 카드값 화면에 "오늘 산 건 카드사 앱에 1~3일 뒤 올라와요" 한 줄.

### H6. 확정일·출금일 설정을 바꾸면 과거 구매의 준비금이 다른 주기로 이동한다
- 준비금은 저장된 값이 아니라 구매일 + 현재 설정으로 매번 역산한다 (`readReserves`). 카드값 행은 안 움직인다.
- 준비금이 카드값 없는 주기로 가면 `fromCash = max(0 − 준비금, 0) = 0`이 되어 준비금이 사라지고, 실제 카드값은 전액 월급에서 빠진다 (보수적).
- 설정 변경은 드물다. 4절에서 `reserve_amount`와 함께 **출금일도 구매 시점에 저장**하면 같이 해결된다.

### H7. 다음 달 예상 현금은 추정치다
- 다음 달 월급·고정지출을 이번 달과 같다고 본다. 다음 카드값은 확정 전 숫자다.
- 4절의 "다음 달 생활비 마이너스면 못 산다"는 이 추정치 위에서 판단하게 된다. 틀릴 수 있다는 걸 알고 쓴다. 보수적으로 틀리는 쪽(막는 쪽)이라 괜찮다.

## 4. 바꾸기로 한 구매 흐름과 계산

### 원칙
- 결제수단은 **실제로 낸 방법**. 기본 현금.
- 카드 결제는 **한 건 전액**이 카드값에 들어간다. 나눠 내지 않는다.
- 다음 달 생활비를 깎는 구매는 **막는다**.

### 흐름

```
초록 (price ≤ shopping)
  → 현금으로 기록. 작은 "카드로 냈어요" 링크 (누르면 카드 기록, 계산은 지금과 같음: 이번 쇼핑 예산에서 빼고 준비금)

빨강 (price > shopping)
  [카드로 산다]       카드값 +price. 다음 달 현금에서 빠진다
                      단, 그 결과 다음 달 생활비 < 0 이면 → 버튼 비활성 + "다음 달 생활비가 X원 모자라요. 다음 달엔 굶어야 돼요" 류 문구
  [생활비를 줄인다]   현금 기록. 넘은 금액만큼 이번 달 생활비 감소 (지금 동작)
                      단, 이번 달 생활비 < 0 이면 → 버튼 비활성
  [안 산다]           기록만
```

두 버튼이 다 막히면 **안 산다만 남는다.** 이게 의도다.

### 결정: 카드로 산다 → 이번 달 쇼핑 예산은 마이너스로 보인다

예: 쇼핑 3만 원 남음, 10만 원 카드 구매.
- 이번 달 쇼핑 예산 **−7만** 표시 (이후 구매는 전부 빨강). 이번 달 생활비는 그대로.
- 준비금 3만 (안 쓰고 남긴 돈을 카드값 몫으로 묶음), 넘긴 금액 7만 → 다음 달 현금 −7만. 카드값은 전액 10만.
- 두 달 합 −10만. 이번 달 남은 예산으로 하나 더 사는 것도 막힌다.

### 스키마

- `decisions.payment_method`: `'account' | 'card'`. 기존 행 null → 카드로 본다 (지금 계산 유지).
- `decisions.reserve_amount`: 카드 구매 중 이번 달 쇼핑 예산으로 묶은 금액 = `min(price, 그 시점 남은 쇼핑)`. 기존 행 → price. 넘긴 금액 = price − reserve_amount.
- `decisions.due_date`: 구매 시점 설정으로 계산한 출금일 저장 (H6 해결, `readReserves`가 역산 안 해도 됨).

### 계산 변경

```
이번 달 소비 spentShopping = Σ 모든 구매 price            (쇼핑 예산은 넘긴 만큼 마이너스로 보인다)
넘긴 금액   deferred      = Σ card 구매 (price − reserve_amount)
쇼핑 예산   shoppingRaw   = cash − 생활비 목표 − 비상금 − spentShopping
생활비      livingNow     = 생활비 목표 + min(shoppingRaw + deferred, 0)   ← 지금은 min(shoppingRaw, 0)
준비금                     = card 구매의 (due_date, reserve_amount)
카드값                     = card 구매 price 전액 (지금과 같음)
→ 다음 달 fromCash = 카드값 − 준비금 = 넘긴 금액이 자동으로 빠진다. 이월 테이블 불필요.
검산: 쇼핑 3만, 10만 카드 → spent 10만, deferred 7만, shoppingRaw −7만, livingNow = 목표 + min(0,0) = 목표. 다음 달 −7만.
```

### 판정 추가 계산 (빨강)

```
카드로 산다 가능?   nextCash − (price − reserve) − 생활비 목표 − 비상금 ≥ −생활비 목표
                   즉 다음 달 생활비 = 생활비 목표 + min(다음 달 쇼핑, 0) ≥ 0
생활비를 줄인다 가능?  livingNow − 넘은 금액 ≥ 0   (지금 judge 의 livingExhausted 반대)
카드로 산다 결과      이번 달 생활비 변화 없음, 쇼핑 예산 = shoppingRaw − price (마이너스 표시)
```
다음 달 생활비 목표·비상금은 아직 설정 전이므로 이번 달 값을 쓴다 (H7).

### 수정 범위
- `lib/budget.ts` judge: 다음 달 생활비 계산 추가
- `lib/decisions.ts` chooseInternal: 결제수단·reserve_amount 저장, addToBill은 card만
- `lib/ledger.ts` computeLedger/readReserves: spentShopping·준비금 계산 변경
- `lib/decisions.ts` cancelInternal: account는 즉시 복구
- 판정 화면: 버튼 3개 + 비활성 문구
- 설정 마법사: "지난 달에서 넘어온 카드 초과분 X원" 표시 (= 이번 카드값 − 준비금 중 앱 구매분)
- `saveMonth` includesCardFixed 버그 (H3) 같이 수정
